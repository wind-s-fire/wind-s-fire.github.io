什么是程序分段

程序分段，通常指的是操作系统和计算机硬件为了更有效地管理内存而采用的一种技术，它把一个程序（或进程）划分成几个逻辑上独立的段。

想象一套本草纲目，不分段的程序就是一本本连续印刷，没有目录，没有分类，也没有分章节的书，想找到水部中的某个草药的某个药性，难度可想而知，但是为什么现实我们能轻松找到水部，因为目录，因为分章节，分纲目，而分段就相当于目录中的“第几章”。

为什么要分段

1·逻辑清晰与管理

  • 程序本身就包含不同的逻辑单元，如代码（指令）、数据、堆（动态分配的内存）、栈（存储局部变量和函数调用的内存），分别体现为text段、data段、堆（Heap）、栈（Stack）以及BSS段（用于存储未初始化或初始化为零的全局变量和静态局部变量）。
  • 分段允许操作系统和硬件以这些自然形成的逻辑单元来管理内存，而不是把一个整体打乱。并且我们可以给不同的段设置不同的访问权限，比如代码段是只读的，数据段可读写但不能执行，这样能有效防止程序错误地修改自己的指令，提升安全性。

2·高效利用内存空间

  • 早期程序必须完全加载到连续的内存空间才能运行，并且运行结束的程序会留下“内存碎片” ，即破碎不连续的内存空间，总体空间足够程序运行，但由于不连续，塞不下程序整体。
  • 分段技术允许一个程序的各个段在物理内存中不连续存放。只要这些段本身是连续的，它们之间可以有空隙。这样，即使物理内存中没有一块足够大的连续空间，只要能找到几块小空间分别容纳各个段的各个页，程序就能运行。
  • 分段技术支持动态增长。程序的栈段或堆段，它们的大小是变化的。比如函数调用越来越深，栈就需要扩大。连续分配中，如果栈段后面紧跟着其他程序或段，栈要扩大就非常困难。分段分配中，因为段是独立的，如果栈段后面有足够的空闲空间，操作系统可以直接把栈段变大。如果后面空间不够，也只需要移动栈段本身（更新段表里的基地址即可），不需要移动整个程序，代价小得多。

3·共享与保护

  • 如果有多个程序在运行同一个程序（比如多个用户同时使用文本编辑器），那么这些程序可以共享内存中的同一个代码段，只需要各自拥有独立的数据段即可。这样可以节省大量内存。
  • 同时，通过段表，可以严格控制每个段是否可以被其他程序访问或修改。

程序通常包含的段

1·代码段/文本段（code/text）

  • 包含程序的机器指令。

  • 通常是只读和可执行的，防止程序在运行时修改自己的代码。

2·数据段（data）

  • 包含已初始化的全局变量和静态变量。
  • 例如：int count = 100; 这里的 count 就存储在此段。

3·BSS段

  • 包含未初始化的全局变量和静态变量。
  • 在程序加载时，系统会将此段内的数据初始化为0。

4·堆（heap）

  • 用于程序运行时动态分配的内存（例如在C语言中用 malloc 申请的内存）。
  • 堆的增长方向通常是从低地址向高地址增长。

5·栈（stack）

  • 用于存放局部变量、函数参数和返回地址。
  • 每次调用函数或从函数返回时，栈都会自动分配或释放内存。栈的增长方向通常是从高地址向低地址（与堆相反）。

各段详解

bss段

定义

bss段（bss segment）通常是指用来存放程序中未初始化的全局变量和静态变量的一块内存区域。

bss是英文Block Started by Symbol（通过符号开始的块）的简称。

bss段属于静态内存分配。

.bss位于.data之后，heap之前

特点

可读可写：程序运行中可修改值。

存储未初始化的变量：.bss段用于存储那些未初始化的全局变量和静态变量。这些变量在程序开始运行之前并没有被赋初值，因此它们在内存中被初始化为0或空值。

节省存储空间：由于未初始化的变量在内存中被默认为0或空值，因此不需要为它们分配实际的存储空间。这种延迟分配的机制可以节省大量内存空间，尤其是当程序中存在大量全局或静态变量时。 .bss段不会占用实际的物理内存空间，在程序加载时只会分配足够的虚拟内存地址空间。只有在程序运行时，才会根据需要分配实际的物理内存页来存储数据。
【虚拟内存地址见《虚拟地址空间》】

提高程序加载速度：由于.bss段不需要在程序加载时实际分配物理内存，所以可以加快程序的加载速度。

简化编程过程：使用.bss段可以方便地定义全局变量和静态变量，并且无需手动初始化它们。这简化了编程过程，并提高了代码的可读性和可维护性。

支持动态内存分配：由于.bss段通常位于数据段之后，堆之前，因此为堆分配的动态内存可以从.bss段的高地址向低地址增长，使得堆和.bss段可以很好地相互配合。

实现原理

程序编译后，生成可执行文件，该文件中，data段收录变量实际数据，分配物理内存并填充数据；bss段收录未定义变量的大小信息，预留虚拟地址空间，标记为”零页“。

data段

定义

data段（data segment）通常是指用来存放程序中已初始化的全局变量和静态变量的一块内存区域。

data段属于静态内存分配。

.data通常位于.text（代码段）之后、.bss之前。

特点

可读可写：程序运行中可以修改data段中变量的值。与text段（只读可执行）形成对比，data段通常不可执行，这种权限分离有效提升了程序安全性。

存储已初始化的变量：data段专门存放那些在定义时已经明确赋予初值的全局变量和静态变量。例如 int count = 100; 中的 count 就存储在此段。

​ 注意：即使初始化值是0，只要显式写出（如 int x = 0;），变量也可能被放入data段而非bss段。

占据磁盘存储空间：这是data段与bss段最本质的区别。由于已初始化变量的值各不相同且必须保留，这些初始值需要实实在在地写入可执行文件中。变量越多、初始值越复杂，可执行文件就越大。而bss段只需在文件头记录”需要预留多少空间”即可，不占实际磁盘空间。

加载时直接拷贝：程序加载时，操作系统从可执行文件中读取data段的原始数据，直接拷贝到物理内存中。不需要像bss段那样做”全零填充”，也不需要触发缺页异常来延迟分配——data段的物理内存在加载时就全部到位。

与只读数据段的区分：需要特别注意的是，C程序中的字符串常量（如 char *s = "hello"; 中的 "hello"）和用 const 修饰的全局变量通常存放在 rodata段（只读数据段），而非data段。rodata段在加载后是只读的，而data段可读可写。"hello" 本身在rodata段，指针变量 s 如果在函数外定义，则在data段（因为它是一个已初始化的全局指针变量）。

【此处关于rodata段的内容在rodata段部分详解】

data段的加载过程（与bss截然不同）：

  1. 分配物理页：操作系统直接从空闲物理页池中拿出一页（4KB）。虽然data段只有2KB，但内存分配以页为单位。
  2. 从磁盘拷贝：将可执行文件中.data段的2KB数据逐字节拷贝到刚分配的物理页中。此时物理页前2KB是 1, 0, 0, 0, 2, 0, 0, 0, 3, 0, 0, 0, 0, 0, ...，后2KB暂时未用（属于同一页的bss段部分，后续会随bss段处理被清零）。
  3. 建立页表映射：将虚拟地址映射到刚分配的物理页。页表项标记为”可读写、不可执行”。
  4. bss段处理：对于bss段，加载器只预留虚拟地址空间，页表项标记为”零页”——不分配物理内存。

rodata段

定义

rodata 段（read-only data segment）通常是指用来存放程序中只读数据的一块内存区域。典型内容包括：

  • 字符串字面量（如 "hello"、"Score table size: %lu\n"）
  • 用 const 修饰的全局变量和静态局部变量
  • switch 语句的跳转表、虚函数表等编译器生成的只读数据结构

rodata 段属于静态内存分配，内容在编译时确定。

特点

只读，不可写：这是 rodata 段最核心的特征。任何试图写入 rodata 段的操作都会触发段错误（Segmentation Fault）。这种保护由硬件 MMU 配合页表权限位实现——操作系统在加载时将 rodata 所在的虚拟页面标记为不可写，CPU 在执行写指令时由 MMU 硬件拦截并触发异常。以字符串字面量为例，"hello" 在 rodata 中，char *p = "hello"; p[0] = 'H'; 会直接崩溃——你试图修改的是 rodata 段的物理页，而非某个局部副本。

不可执行：rodata 段通常不具备可执行权限（尽管部分老式系统可能将 rodata 和 text 合并或赋予相同权限）。现代操作系统严格贯彻 W^X 原则——一页内存不能同时可写和可执行，rodata 虽只读但也不可执行。

内容编译时确定，加载时就位：rodata 中的所有数据在编译阶段就已确定并写入可执行文件。程序加载时，操作系统将 .rodata 段的字节从磁盘文件直接映射到虚拟地址空间中的只读页面。不涉及运行时计算，不需要像 bss 段那样延迟分配。

字符串合并优化：编译器通常会对相同的字符串字面量做合并（string pooling），多个 "hello" 在 rodata 中只存一份。这既省磁盘也省内存。

rodata 与 data 的一个关键结构性差异：进程间共享

rodata 段内容在整个程序生命周期内不会改变，这带来一个 data 段不具备的能力：rodata 可以被同一可执行文件的所有运行实例（进程）安全地共享同一份物理页面。

以文本编辑器为例：你同时打开了 5 个编辑器窗口（5 个进程）。如果编辑器二进制有 2MB 的 .data 段，每个进程都需要各自独立的 2MB 物理内存（因为各自的全局变量值不同）；但如果编辑器还有 800KB 的 .rodata（含界面字符串、菜单结构、错误消息等），操作系统可以让这 5 个进程映射到同一块 800KB 物理内存。读的时候各读各的，写是不可能的（反正谁也写不了），所以谁也不会干扰谁。

这是 data 段做不到的——因为 int x = 100; 之后某进程随时可能改成 200，共享会导致互相覆盖。rodata 天然不可变，天然适合共享，这既是安全特性也是性能优化。

text段

定义

text 段（text segment），也称为代码段（code segment），通常是指用来存放程序机器指令的一块内存区域。CPU 执行的每一条指令——算术运算、内存读写、函数调用、条件跳转——都从 text 段中逐条取出。

text 段属于静态内存分配，内容在编译时确定，运行期间不可修改。

.text 通常位于虚拟地址空间的最低区域（如 0x00400000 起），处于 rodata 段、data 段和 bss 段之前。

特点

只读，不可写：text 段被操作系统标记为只读权限。任何试图写入 text 段的行为（如程序错误地修改自身代码）都会触发段错误（Segmentation Fault）。这种保护由*硬件 MMU*配合页表权限位实现——加载时将 text 所在页标记为不可写，写指令在 MMU层面即被拦截。这也是抵御缓冲区溢出攻击（攻击者试图向代码区注入恶意指令）的第一道硬件防线。

可执行：text 段是所有段中唯一具备可执行权限的。CPU 的程序计数器（PC / RIP）指向 text 段中的地址，取指单元（instruction fetch unit）从该地址读取指令字节，送入解码器执行。rodata段虽然也存放字节序列，但没有执行权限——如果把 rodata的地址当作函数指针调用，MMU同样会拦截并触发段错误。

不可变，静态大小：text 段的内容（机器码）在编译链接后完全确定，大小固定。不像堆可以 malloc 扩张，也不像栈随函数调用伸缩。程序运行期间 text 段的大小永远不变。

内容编译时确定，加载时就位：编译器将 C 代码翻译为机器指令，链接器将各目标文件的 .text 合并为最终可执行文件的 .text 段。加载时操作系统将该段从磁盘直接映射到虚拟地址空间的只读可执行页面，不涉及任何运行时计算或延迟分配。

进程间共享：这是 text 段区别于 data 段和栈的最重要特征。同一个可执行文件的多个运行实例（多个进程）可以共享内存中的同一份 text 段物理页面。操作系统利用虚拟内存机制，让各进程的页表将各自的虚拟地址映射到同一组物理页。由于 text 段只读不可写，不存在互相干扰的风险。具体场景：你同时打开 3 个终端窗口，每个运行着 /bin/bash，内存中只需要一份 bash 的 text 段，而非三份。rodata 段也具备此能力；data 段和 bss 段因各自数据不同，每个进程必须持独立副本.

实现原理

text 段的生命周期与 data 段和 rodata 段类似——编译时写入可执行文件，加载时一次性映射。区别在于权限位：text 标记为「可读可执行（R-X）」，data 标记为「可读可写（RW-）」，rodata 标记为「只读（R–）」。运行时，text 段不涉及”写入”操作，而是作为 CPU 取指执行的唯一指令来源。

heap（堆）

注：由于堆栈的理解在pwn的学习中较为重要，并且两者联系较为紧密，所以后续会单独写一份堆栈的详细运行、理解以及一些运行的特殊情况。

定义

heap（堆）是进程虚拟地址空间中用于动态内存分配的一块区域。与 data 段和 bss 段的静态分配不同，堆中的内存是在程序运行期间通过 malloc、calloc、realloc 等函数按需申请、通过 free 释放的。堆的大小不固定，随程序的运行动态伸缩。

堆位于 data 段 / bss 段之上、内存映射区域（mmap 区域）之下，从低地址向高地址增长（与栈的增长方向相反）。

在 Linux 中，堆的底层由两个系统调用驱动：brk/sbrk（调整堆顶指针，适用于小块内存）和 mmap（在堆和栈之间的映射区域单独分配，适用于大块内存）。

特点

可读可写：堆中的内存由用户程序自由读写。与 text 段（只读可执行）和 rodata 段（只读）形成鲜明对比，堆与 data 段、bss 段、栈一样具备读写权限。

动态大小，运行时伸缩：这是堆区别于所有静态段（text、rodata、data、bss）的核心特征。堆的大小不是编译时确定的——程序可以通过 malloc 随时申请更多内存，通过 free 释放不再需要的空间。堆的边界由 break 指针（也称 program break）标记，brk/sbrk 系统调用可以将该指针向高地址推移来扩大堆，也可以在条件满足时向低地址回缩。

延迟分配物理内存：堆与 bss 段一样，采用”用时再给”的策略。malloc 返回的虚拟地址在首次被访问之前，页表中对应的条目可能标记为未分配。只有当 CPU 第一次读取或写入该地址时，才触发缺页异常（page fault），操作系统在异常处理中分配物理页、清零（仅对匿名页）、建立虚拟地址到物理地址的映射，然后 CPU 重新执行被中断的指令。这意味着 malloc(1GB) 调用本身几乎瞬时完成，而实际的物理内存开销分散在后续的逐页访问中。

释放不一定归还操作系统：free 释放的内存通常不会立即通过 brk(-size) 归还给操作系统。glibc 的 ptmalloc 分配器会将释放的块加入空闲链表（free list），供后续 malloc 重用。只有当堆顶出现足够大的连续空闲空间（默认阈值约 128KB）时，分配器才可能调用 brk 将 break 指针向低地址回退，真正释放物理内存。这意味着：即使程序已经 free 了大量内存，从操作系统视角看，进程的 RSS（常驻内存集）可能并未下降。

内存碎片问题：频繁的 malloc 和 free 会在堆中产生碎片——释放的块之间被仍在使用的块隔开，导致虽然总体空闲空间充足，却没有一块足够大的连续空间来满足某次分配请求。brk 方式分配的堆内碎片尤其顽固：只要堆顶附近仍有未释放的块，break 指针就无法回退，其下方即使有再大的空闲空间也无法归还操作系统（详见实现原理中的内存空洞问题分析）。

两种底层分配路径：glibc 的 malloc 根据请求大小选择不同策略——

  • 小块内存（默认 < 128KB）：通过 brk/sbrk 推移 break 指针，在堆的连续区域内分配。释放后可被重用，减少系统调用和缺页中断开销。
  • 大块内存（默认 ≥ 128KB）：通过 mmap 在堆上方的映射区域单独分配匿名内存页。释放时直接 munmap，物理内存和虚拟地址空间一并归还，不产生持久碎片。阈值可通过 mallopt(M_MMAP_THRESHOLD, ...) 调整。

堆与栈的增长方向相反：堆从低地址向高地址增长，栈从高地址向低地址增长。两者相向而行，中间夹着 mmap 映射区域。这种布局使得堆和栈可以灵活地利用中间的空闲地址空间，而不会在编译时相互硬性限制。

实现原理

堆的实现涉及两层：用户态分配器（glibc malloc / ptmalloc）和内核态系统调用（brk、mmap）。分配器负责将内核提供的大块内存切割为小块、管理空闲链表、合并相邻空闲块；内核负责维护虚拟地址空间和物理页之间的映射。

只有当 malloc → brk 被推高 → 地址从 unmapped region 划入 mapped region 之后，访问该地址才能触发良性的缺页异常（分配物理页）而不是段错误。这里区分两个概念很重要：

  • 访问 mapped region 内尚未分配物理页的地址 → 良性的缺页异常 → 内核分配物理页 → 程序继续运行。
  • 访问 unmapped region（brk 之上）的地址 → 非法的缺页异常 → 内核判定该地址不在任何有效 VMA 内或超出边界 → SIGSEGV 终止进程。

两者的外在症状相似（都触发缺页异常），但内核的裁决逻辑完全不同：前者是”合法但延迟”，后者是”非法访问”。

brk 路径（小对象）
  1. 用户态（ptmalloc）：glibc 的 malloc 检查内部空闲链表，发现没有可用块（程序刚启动，堆还为空）。
  2. 向内核申请：ptmalloc 调用 brk(old_break + 128KB)（实际上一次不会只申请 100 字节——为了减少系统调用，分配器会一次性向内核申请较大块，如 128KB 或更大，然后从中切出 100 字节给用户）。
  3. 内核处理：sys_brk 将进程 mm_struct 中的 brk 字段更新为新值。此时仅修改了虚拟地址空间的边界——物理页仍然没有分配。内核只在 VMA（虚拟内存区域）中记录”堆的范围扩大到了 0x00424000”。
  4. 返回用户：ptmalloc 从刚申请的 128KB 大块中切出约 112 字节（100 + chunk header 元数据），记录该 chunk 的大小和状态，返回指向有效载荷区域的指针给 small。
  5. 首次写入触发缺页异常：执行 strcpy(small, "hello heap"); 时，CPU 尝试写入 small 指向的虚拟地址。MMU 查页表 → 该虚拟地址尚未映射物理页 → 触发缺页异常（page fault）。
  6. 缺页异常处理程序：内核识别到这是堆区域内的合法地址 → 从空闲物理页池中拿一个 4KB 页 → 将该页清零（安全要求：不能泄漏前一个进程的数据）→ 建立该虚拟页到该物理页的页表映射（权限 RW-）→ 返回用户态，CPU 重新执行 strcpy 指令。
  7. 后续写入：small[0] = 'H'; 时，small 仍在同一物理页内，页表已有映射，直接写入，不触发缺页异常。
mmap 路径（大对象）

large = (char*)malloc(1024 * 1024); 超过 128KB 阈值，ptmalloc 不走 brk，而是：

  1. 调用 mmap(NULL, 1MB + overhead, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)。
  2. 内核在 mmap 映射区域（堆和栈之间）找一块 1MB 的虚拟地址空间，建立 VMA，标记为匿名私有映射。（”映射”部分见《虚拟内存》）

  4. memset(large, 0x41, 1024 * 1024); 写入 1MB 数据时，每遇到一个之前未访问的 4KB 页，就触发一次缺页异常 → 内核分配物理页 → 清零 → 映射。1MB 共触发 256 次缺页异常（1MB / 4KB = 256 页）。
释放
  • free(small)：ptmalloc 将 small 对应的 chunk 标记为空闲，插入空闲链表。但由于 small 不在堆顶，break 指针不移动，物理内存不归还。

内存空洞问题

文中 bss 段和 data 段部分详细讨论了缺页异常和延迟分配的好处，但堆还有一个独有的”陷阱”值得注意：内存空洞。

考虑以下场景：

此时堆顶 C（300KB）仍在占用，所以尽管 A 和 B 对应的物理页已经释放（加入空闲链表），但 break 指针无法回退——因为 brk 机制只能通过移动堆顶指针来收缩线性区，而堆顶被 C 挡住。

后果：A 和 B 的虚拟地址空间无法归还操作系统（VMA 未收缩），其物理内存虽然已被标记为空闲、可能被后续同大小请求重用，但在操作系统眼中，进程的 RSS 并没有减少。这就是”堆内碎片”的本质——从进程视角是空闲的，从操作系统视角仍在占用。

mmap 路径之所以不存在此问题，是因为每个 mmap 大块在虚拟地址空间中独立成区，munmap 可以精确释放该区域，无需等待”堆顶”条件满足。这也是 glibc 对大块分配默认走 mmap 的核心原因之一。

stack（栈）

（同上）注：由于堆栈的理解在pwn的学习中较为重要，并且两者联系较为紧密，所以后续会单独写一份堆栈的详细运行、理解以及一些运行的特殊情况。

定义

stack（栈）是进程虚拟地址空间中用于管理函数调用的一块内存区域。它存放局部变量、函数参数、返回地址以及需要保存的寄存器值。与堆通过 malloc/free 显式管理不同，栈的分配和释放是自动的——由编译器生成的指令和 CPU 的栈指针寄存器（rsp）在每次函数调用与返回时自动完成。

栈位于进程虚拟地址空间的高地址区域，从高地址向低地址增长（与堆的增长方向相反）。在 Linux 中，主线程栈的初始大小默认约为 8MB（受 ulimit -s 限制），线程栈通常为 2MB（受 pthread 属性控制）。

特点

可读可写：栈中的局部变量、函数参数等数据在函数运行期间可自由读写。

后进先出（LIFO）：栈的分配与释放严格遵循后进先出顺序——最后进入的栈帧最先被销毁。函数调用越深，栈帧层层叠加；函数返回时，最上层的栈帧先被弹出。这种结构与函数调用的嵌套关系天然吻合。

自动分配与释放：栈的伸缩完全由编译器生成的指令驱动，程序员无法（也无须）手动管理。函数进入时，编译器生成 sub rsp, N 指令扩大栈；函数返回时，leave 或 add rsp, N 指令收缩栈。整个过程没有任何”申请内存”的系统调用，只是寄存器加减。

大小受限，易溢出：栈的地址空间有固定上限（Linux 主线程默认 8MB）。如果递归过深或局部数组过大，栈指针越过上限，就会触发栈溢出（Stack Overflow）——访问到保护页之外的非法地址，内核发送 SIGSEGV 终止进程。这与堆的”按需增长”形成鲜明对比。

增长方向：高地址 → 低地址：栈从高地址向低地址增长，堆从低地址向高地址增长，二者相向而行，中间夹着 mmap 映射区域，从而可以灵活利用中间的空闲地址空间。

延迟分配物理内存：栈与堆、bss 段一样，采用”用时再给”的策略。栈指针移动本身只是调整寄存器，不分配物理内存；只有当 CPU 首次读写某个新的栈页时，才触发缺页异常，内核分配物理页、清零、建立映射。

缓存友好：栈上的数据遵循严格的局部性——相邻变量存储位置接近，频繁访问的数据集中在栈顶附近，因此 CPU 缓存命中率极高。

线程隔离：每个线程拥有自己独立的栈（线程栈），栈中保存的数据天然是线程私有的，不存在跨线程竞争问题。而堆则是进程内多个线程共享的。

实现原理

栈的实现完全由编译器和 CPU 寄存器驱动，不依赖任何系统调用。核心是两个寄存器：

  • rsp（栈指针）：始终指向栈顶（当前函数可用栈空间的最低地址）。
  • rbp（帧指针）：指向当前栈帧的底部（基准地址），用于定位局部变量和参数。

阶段二：程序加载

操作系统加载器解析可执行文件，建立进程的虚拟地址空间布局。与堆”加载时零字节”不同，栈在加载时就预先分配了几页物理内存。原因在于：程序在进入 main 之前，_start 启动代码、动态链接器 ld.so 以及 execve() 本身都需要向栈中写入数据（环境变量、命令行参数、auxv 辅助向量等），因此栈的初始几页必须在加载时立即就绪。

Linux 内核在 execve() 加载可执行文件时，会完成以下栈初始化：

  1. 确定栈顶地址：将栈放置在虚拟地址空间的高地址区域（x86-64 下通常在 0x7FFF… 附近），栈顶指针指向该高地址。
  2. 写入初始数据：从高地址向低地址依次压入——环境变量字符串、命令行参数字符串、argv 指针数组、envp 指针数组、argc、auxv 辅助向量等。
  3. 分配初始物理页：为已写入的数据分配物理页并建立映射（这部分栈页立即有物理内存）。
  4. 设置栈指针：将 rsp 指向初始数据之后的位置，等待 _start 使用。

关键点：加载时栈的初始状态是”顶部已有几页数据、底部指针就绪”，而堆的初始状态是”零字节、无任何映射”。这是二者初始状态最本质的差异——栈”出生即带数据”，堆”出生一无所有”。

阶段三：运行时

步骤 CPU 动作 rsp 变化 说明

2 mov rbp, rsp：建立 add 的新栈帧 不变 rbp 指向新帧底
3 sub rsp, 16：为 sum 预留空间 rsp -= 16 局部变量空间（尚未访问，暂无物理页）
4 写 sum：mov [rbp-4], eax 不变 首次写入可能触发缺页异常 → 分配物理页

6 ret：弹出返回地址，跳回 main rsp += 8 返回调用者

关键机制——栈的缺页异常：

栈指针移动（sub rsp, 16）本身只是寄存器减法，不分配任何物理内存。当 CPU 首次访问新划入栈范围的地址（如步骤 4 写入 sum）时：

  1. MMU 查页表 → 该虚拟页未映射物理页 → 触发缺页异常。
  2. 内核检查该地址是否在栈的 VMA 范围内 → 合法（属于栈增长区域）。
  3. 分配一个空闲物理页 → 清零 → 建立映射（RW-）。
  4. 返回用户态，CPU 重新执行写指令。

栈的自动增长机制：

当函数调用越来越深、栈指针持续下移，最终触碰到栈的保护页（guard page）时，内核检测到这是栈的合法增长需求，会自动扩大栈的 VMA 边界（而非像普通非法地址访问那样直接 SIGSEGV）。Linux 内核通过”栈自动增长”机制，让栈在默认上限内平滑扩张。

栈溢出（Stack Overflow）：

如果递归过深或局部数组过大，栈指针越过上限（默认 8MB），访问保护页之外更远的地址，内核判定为非法访问，发送 SIGSEGV 终止进程：

stack 与 heap 差异详解

初始状态差异

维度 栈（Stack） 堆（Heap）
加载时物理内存 预分配几页（含 argc/envp/auxv 等初始数据） 零字节（start_brk == brk，无任何映射）
加载时指针状态 rsp 已指向初始数据之后，可立即使用 brk 指向 data/bss 末尾，尚无任何可用空间
产生差异的原因 程序进入 main 前必须向栈写数据（参数、环境变量等） 编译器无法预知运行时 malloc 多少，故从零开始
首次使用行为 直接读写已就绪的初始页 必须先 malloc → brk 上移 → 才有可访问地址

扩张方式差异

维度 栈（Stack） 堆（Heap）
扩张触发者 编译器生成的指令（push/call/sub rsp） 程序员的 malloc 调用
扩张机制 寄存器 rsp 下移 + 内核自动增长 VMA brk 上移（小块）或 mmap 新映射（大块）
是否有系统调用 通常无（仅 rsp 加减；触及 guard page 时内核自动扩张） 有（brk/mmap 系统调用）
扩张粒度 每次函数调用伸缩任意字节（如 16 字节） 分配器一次向内核申请大块（如 128KB）再切分
收缩行为 函数返回 rsp 上移，物理页保留复用 free 后不一定归还 OS，仅加入空闲链表
扩张失败表现 栈溢出（SIGSEGV），进程崩溃 malloc 返回 NULL，程序可自行处理

核心结论：栈的扩张是”免费的”——只是寄存器加减，不涉及系统调用；堆的扩张是”有代价的”——每次实质扩张都需要 brk/mmap 系统调用。这也是栈分配速度远快于堆的根本原因。

其他关键差异

维度 栈（Stack） 堆（Heap）
数据组织结构 严格 LIFO，栈帧嵌套 任意，由分配器维护空闲链表
碎片 无碎片（连续回收） brk 路径有碎片，mmap 路径无
生命周期管理 自动（随函数进出） 手动（程序员负责 free，易泄漏）
线程关系 每线程独立栈 堆为进程内多线程共享
缓存局部性 极佳（栈顶集中访问） 较差（对象分散，无固定顺序）
典型故障 栈溢出（递归过深、大数组） 内存泄漏、野指针、碎片

注意：

现代的栈与堆一样，同样采用延迟分配（demand paging）机制——栈指针移动不分配物理内存，首次访问新页时才触发缺页异常分配。二者唯一的初始差异在于：栈在加载时预分配了初始几页（因为 execve() 需要向栈写入参数和环境变量），而堆加载时为零字节。除此之外，栈的扩张（rsp 下移 + guard page 自动增长）与堆的扩张（brk/mmap）在”物理页延迟分配”这一点上是完全一致的。

（”延迟分配机制”见《虚拟内存》的映射部分）
