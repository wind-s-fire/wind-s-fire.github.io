物理内存

发表于2026-11-10|更新于2026-11-10|pwn
|浏览量:

定义

内存分配：计算机里的”画地盘”

内存分配，简单来说就是程序向操作系统申请一块内存空间，用来存放数据。

分类

三种分配方式：按时间划分

内存分配不是只有一种。根据”什么时候圈地”来划分，可以分成三类：静态分配（编译时）、自动分配（运行时-栈）、动态分配（运行时-堆）。

以下详解

静态内存分配

静态内存分配的核心就一句话：编译器在编译阶段就知道这块数据需要多大、放在哪里，程序还没开始跑，地址和大小都已经写死在可执行文件（ELF）里了。

你盖一栋房子。承重墙的位置和尺寸是画在设计图上的，地基一浇就固定下来，整栋房子的寿命有多长，这堵墙就立多久。你不能在房子盖好之后说”我觉得这堵墙挡住了阳光，拆了吧”——它天然就该在那里，而且永远在那里。

静态分配的数据就是程序的”承重墙”——全局变量、静态变量、字符串常量这些东西，链接器在生成可执行文件时就已经给它们分配好了地址，操作系统加载程序时按图索骥，一口气把它们扔进内存里固定位置。程序退出前，这些位置从不挪窝，也从不释放。

全局变量和静态全局变量：编译时就知道需要多少内存；

静态局部变量：虽然是局部作用域，但内存是编译时确定的；

自动内存分配

自动分配发生在函数调用时，分配在栈上，是函数块引起的内存变化。函数一进来，栈指针往下一挪，挤出一点空间给局部变量用；函数一返回，栈指针弹回原位，刚才占的那块地立刻作废（残留垃圾值），谁再踩上去谁倒霉。

自动变量就像出差住酒店——你入住时分到一个房间，退房那一刻房间就不再属于你了。下次再来住，大概率是另一个房间，里面可能还残留着上一个房客的痕迹（这也是为什么未初始化的局部变量是垃圾值）。

垃圾值来源

对于栈

进程启动时，栈就已经分配好了一定大小的虚拟内存区域（Linux 默认 8MB）。这块区域在整个进程的生命周期里反复使用——函数调用时栈指针往下走（”借”空间），函数返回时栈指针往上走（”还”空间），但只是挪指针，从来没有擦除内容。

这时，垃圾值是同一个进程里，上一次栈使用留下的旧数据，不是别的进程留下的。它来自你自己的程序，来自之前某个已经返回的函数调用的残留。

对于堆

malloc 返回的内存也有”未初始化即垃圾值”的问题。但来源同样是同进程内的历史操作：

  • malloc 底层调用 brk 或 mmap 向操作系统要内存
  • 操作系统给的新页面是清零的（zero-fill）
  • 但 malloc 内部维护了一个空闲链表——你 free 掉的内存不会立刻还给操作系统，而是留在链表里等着下次复用
  • 下次 malloc 从链表里拿一块给你时，上面还沾着你上次 free 之前写过的旧数据，并不清零

所以堆上的垃圾值，也来自同一个进程的历史操作。区别只在于栈是函数调用链的残留，堆是 malloc/free 复用机制的残留。

动态内存分配

动态分配发生在程序运行时，由程序员显式申请（malloc / new），在堆上找空闲内存。什么时候申请、申请多大、什么时候释放，全由程序员决定。忘了释放就是内存泄漏，提前释放了还用就是野指针。

静态分配是自家后院盖的仓库——永久产权，终身使用。动态分配是去菜市场临时租摊位——你想租几个、租多大、租多久，当场谈。但开市结束你得自己收拾走人，忘了退租，市场管理员就当你一直占着。

表格对比

静态分配 自动分配 动态分配
决定时机 编译时 编译时（大小）+ 运行时（实际分配） 运行时
存放位置 静态数据区（.data / .bss） 栈 堆
生命周期 程序启动到结束 进入函数到离开函数 自由控制（malloc 到 free）
速度 最快（地址直接编码进指令） 很快（改一个栈指针寄存器） 较慢（要在堆里搜索空闲块）
大小限制 编译时必须是常量 栈空间有限（几 MB） 几乎只受物理内存限制
释放责任 操作系统自动回收 自动回收 程序员手动释放
典型例子 全局变量、静态变量、字符串字面量 函数局部变量 malloc / new 申请的内存

对于静态分配的部分解释

“静态”在这里不是”静止不动”的意思，而是**”编译时就确定、运行时不改变”**。

编译器看到 int global_x = 10;，它就知道：这个东西需要 4 个字节，值从 10 开始，地址就定在数据段的某个偏移量上，这辈子不会变。链接器把它写进可执行文件的元信息里，加载器按图索骥，一瞬间搞定。

所以静态分配的数据，速度快（地址在指令里硬编码，不用间接寻址），但灵活性差（数组大小必须是编译时常量，不能根据用户输入动态调整）。这也是为什么 C99 之前不允许变长数组，也是为什么静态局部变量的大小不能依赖函数参数——编译器必须提前知道该给你留多大的地。

物理内存管理

MMU（内存管理单元）

定义

MMU，全称 Memory Management Unit（内存管理单元），是 CPU 内部（或紧邻 CPU）的一块硬件组件。它不是软件，而是硅片上实实在在的电路。MMU 的核心职责有两个：地址转换和权限检查。每一次 CPU 发出的内存访问请求，都必须经过 MMU 的审查才能到达物理内存。

地址转换

虚拟地址 → 物理地址

现代操作系统给每个进程分配独立的虚拟地址空间（如 32 位系统下的 4GB）。进程”以为”自己独占全部内存，但实际上多个进程的虚拟地址被映射到不同的物理页上。MMU 通过页表完成这个转换。（“虚拟地址”部分详见《虚拟内存》；“页表”见《页的概念》）

页表由操作系统维护，存储在物理内存中。每条页表项（PTE）记录了一个虚拟页面对应的物理页框号，以及该页的权限位。CPU 发出虚拟地址后，MMU 将其拆分为”页号 + 页内偏移”，以页号为索引查页表，找到物理页框号后拼接偏移，得到物理地址。

（后话）为了加速这个过程，MMU 内部还集成了 TLB（Translation Lookaside Buffer，转换后备缓冲）——一个缓存最近地址映射的高速小存储，命中的话几乎零延迟完成转换。

权限检查

段错误的直接来源

MMU 在查页表的同时，会读取每个页表项中的权限位。典型权限包括：

权限位 text 段 rodata 段 data 段 栈/堆
R（可读） ✓ ✓ ✓ ✓
W（可写） ✗ ✗ ✓ ✓
X（可执行） ✓ ✗ ✗ ✗

text 段是所有段中唯一具备可执行权限的，CPU 的取指单元在每次读取指令前由 MMU 检查页表——如果当前指令指针指向的页面没有 X 权限，MMU 直接触发段错误。

同理，如果 CPU 试图向 R-X 或 R– 页面写入数据，MMU 比对权限时发现 W 位为 0，也立即拦截。

实现原理：完整的段错误流程

下面以”程序试图修改 text 段中的一条指令”为例，完整追踪一次段错误的发生过程：

第一步：加载时设立防线。 操作系统加载可执行文件时，解析 ELF/PE 段表中的权限信息，为 text 段建立页表项并将其权限位设为 R-X（可读、可执行、不可写），为 rodata 段设为 R–，为 data 段设为 RW-。这些页表项写入物理内存后，操作系统用特权指令告诉 MMU 页表的基地址。

第二步：程序发出违规写指令。 假设程序由于 bug 将 text 段的某个地址当作数据地址来写——CPU 执行单元发出一条 mov [text_addr], value 的存储指令。

第三步：MMU 拦截。 存储指令触发内存访问，MMU 接管。MMU 查页表（或 TLB）找到 text_addr 对应的页表项，检查权限位：W 位 = 0。权限校验失败。

第四步：硬件触发异常。 MMU 不向内存总线发出任何信号——它直接向 CPU 内核发出一个页故障（page fault）异常信号。CPU 从用户模式切换到内核特权模式，保存现场（寄存器、指令指针等），跳转到操作系统的页故障异常处理程序。值得注意的是，此时异常类型是”权限违规”而非”页面不存在”。

第五步：操作系统裁决。 内核的页故障处理程序检查异常详情：

  • 如果是”页面不在物理内存”（如被 swap 换出），内核会从磁盘调入页面并重试——这是正常的缺页中断。
  • 如果是”权限违规”——即此次的情况——内核判定该进程试图非法访问内存，向进程发送 SIGSEGV 信号。

第六步：进程终止。 进程如果未注册 SIGSEGV 的自定义处理函数，默认行为是立即终止。操作系统输出 “Segmentation fault (core dumped)”，程序崩溃。

整个过程中，最关键的一点是：拦截发生在硬件层，而非软件层。 不是操作系统在每条指令后”检查一眼代码有没有乱写”——操作系统根本不可能有那样的效率。而是 MMU 作为 CPU 和内存总线之间的必经之闸，在地址翻译的同时顺手完成权限比对。不合规的访问连内存控制器都到不了，在这道闸口就被拦下了。
